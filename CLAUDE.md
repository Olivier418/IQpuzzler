# Codebase map

Core model, layered bottom-up:
- `classes/lattice.py` — `Lattice`: geometry of a board/block's axes (orthogonal vs. offset, e.g. triangular/pyramid). Derives gram2 / unit_vectors / `point_group` (every integer matrix `M` with `M.T @ gram2 @ M == gram2`, i.e. the lattice's rotations/reflections — 8 for the square lattice, 48 for the pyramid's; says nothing about any particular board's cells, which is what `Setup.region_symmetries` intersects it with) / neighbor_structure. Leaf, no deps.
- `classes/blocks.py` — `Block` (shape + color/letter + its own Lattice), `BlockCollection` (UserDict, int idx -> Block, unique letters).
- `classes/boards.py` — `Board` (cells: bool ndarray + Lattice), `RegularBoard`, `PyramidBoard` subclasses.
- `classes/puzzle.py` — the big one:
  - `Setup`: board + blocks + **all valid placements** (expensive, computed once, shared by reference across every Puzzle/Book built on it). `placements[block_idx]` = flat cell-index array per valid orientation/position. `render(grid, header=None, leftover_idcs=None)` is a thin facade delegating to `classes/rendering.py` -- the shared basis for every `__repr__` below. Also owns the symmetry geometry the solver's modes 3/4 run on: `cell_coords` (compact index -> board coords), `region_symmetries(mask)` (every symmetry of an *arbitrary* sub-region of the board's cells, as compact-index permutations that are the identity outside the mask; only the lattice `point_group` is searched, since a finite region admits at most one translation per matrix), and `board_symmetries` = `region_symmetries(all cells)`, cached. Mode 4 calls `region_symmetries` at nearly every search node, so it's written as a few array ops over precomputed tables rather than a per-matrix loop: `_point_group_coords` -> `_symmetry_tables` flattens every cell's position under every matrix into a *padded* grid (sized from those positions' own extremes so nothing wraps an axis, which makes flattening linear and order-preserving -- a translation is then a scalar add and "lex-smallest cell" is a `min`), with off-board positions mapping to an `n_cells` sentinel. Being onto needs no cell-set comparison: the map is injective, so `m` images landing inside an `m`-cell region is already all of it.
  - `State`: mutable solve state (grid + chosen_placement_idx) over a shared `Setup`. `place`/`remove` (checked) vs `place_unchecked`/`remove_unchecked` (used by Solver, no overlap/UNPLACED checks). `.solve()` delegates to `Solver.py`. `render(show_leftover=True)` (via `_print_header`, overridable) builds header + grid + shape diagrams of any still-unplaced blocks; `__repr__` calls it with the default, so `print(state)` just works. `show_leftover=False` is used when a container prints many puzzles at once and the per-puzzle legend would just be noise.
  - `Puzzle(State)`: named, has difficulty, optionally pre-filled from a letter grid (`_initialize_grid`, transposes JSON (depth,width) -> internal (width,depth)). Overrides `_print_header` to `"Puzzle {name}"`.
  - `PuzzleBook(UserDict)`: named collection of Puzzles sharing one Setup. `__repr__` expands every contained Puzzle in full, with `show_leftover=False` (a puzzle printed on its own still shows its unplaced blocks; one printed as part of a book doesn't).
- `classes/game.py` — `Game`: top-level container of `books` (dict name->PuzzleBook), `puzzles` (standalone), `setups` (dict board_key->Setup). One Game per `games/<GameName>/` folder. `__repr__` expands every book and standalone puzzle in full.
- `classes/source.py` — `Source` (frozen dataclass): game/book/puzzle name triple recording where a Puzzle/Book was loaded from, so solutions can be auto-saved to a mirrored path. `relative_dir()` maps it to that path: a whole book -> `<game>/books/<book>`, a standalone puzzle -> `<game>/puzzles/<puzzle>`, one puzzle solved out of a book -> nested under its book (`<game>/books/<book>/<puzzle>`), never concatenated into one name, so it's always unambiguous to split back apart. Set by `serialization.loading.load_game`, `None` for hand-built objects.
- `classes/solutions.py`: solutions (deterministic, since the solver is exhaustive) and solve-process metadata (mode/seed/duration/timing, which *isn't* deterministic) are deliberately separate object pairs -- see `serialization/` below for how they're saved.
  - `PuzzleInfo` (NamedTuple: difficulty, nr_empty_spaces) — the source Puzzle's, not the Solution's own; never stored on `Solution`, only returned on demand (see below) so it can't drift from the Puzzle.
  - `SolveStats` (NamedTuple: puzzle_name, mode, seed, duration, elapsed) — metadata about one solver run; `elapsed` is per-solution elapsed time, index-aligned with the matching `Solution.grids`.
  - `Solution`: puzzle_name + `grids: list[np.ndarray]` + game/book_name (transient in-memory metadata only -- never written to disk, since the save folder already determines them; on reload they're recovered from the folder path instead) + optional live `puzzle` ref (not persisted; `.setup` is a property reading `puzzle.setup`). `.from_puzzle()` solves and returns `(Solution, SolveStats)`, optionally auto-saving both (always `flat=True`: one puzzle's solutions, standalone or out of a book -- see `serialization/saving.py`). `.to_states()` hydrates `grids` back into live `State` objects (uses the live puzzle's setup if present, else `load_setup_for_puzzle`). `.puzzle_info(puzzles=None)` resolves the source Puzzle's difficulty/nr_empty_spaces -- straight off the live `puzzle` if present, else from `puzzles` (a PuzzleBook/dict) if given, else `load_puzzle_info_for_puzzle` (no Setup needed). `__repr__` hydrates via `to_states()` and renders each grid as "Solution {i} to puzzle {name}" (via `Setup.render`).
  - `SolutionBook(UserDict)`: puzzle_name -> Solution, plus book-level game/book_name (same transient/not-persisted rule as `Solution`). `.name` is a computed property (`book_name`, or -- for a book-less single-puzzle book -- that puzzle's name), not a stored field, so it can't drift from `book_name`. `.from_puzzlebook()` batch-solves via `Solution.from_puzzle`, returning `(SolutionBook, SolveStatsBook)`, always saved as one combined `flat=False` file (a `"puzzles"` list) regardless of book size, never split into per-puzzle folders. `__repr__` expands every contained Solution in full.
  - `SolveStatsBook(UserDict)`: puzzle_name -> SolveStats, plus book-level game/book_name/mode/seed. `.name` computed the same way as `SolutionBook.name`. Produced alongside its matching `SolutionBook` by the same solve call; never built standalone.
- `classes/rendering.py` — terminal display, split out of `Setup` since it's a display concern, not part of the board/blocks/placements model: `grid_lines(board, blocks, grid)` (ASCII/color board rendering as a list of row strings), `block_shape_lines(block)` (a single block's own shape, from `block.coords`, as a small standalone diagram -- returns lines + width in cells, since colorama escape codes make raw string length meaningless for alignment), `legend_lines(blocks, block_idcs, max_width_cells=None)` (lays out several blocks' shape diagrams side by side, wrapping onto further rows once `max_width_cells` is exceeded -- used for a State's unplaced blocks), `render(board, blocks, grid, header=None, leftover_idcs=None)` (header + grid + leftover-block legend underneath, composed into one string). Operates on plain `Board`/`BlockCollection`/grid args, no dependency on `Setup`.
- `classes/_utils.py` — `_assert_unique`, `_shared` (dedup/consistency helpers used across the above), `_next_free_idx_dir(base, prefix="result")` (base/{prefix}_1, base/{prefix}_2, ... -- shared per-run-folder numbering used by `classes/solutions.py`, `serialization/saving.py` (default `"result"` prefix), and `plotting/benchmark.py` (`"benchmark"` prefix)).
- `classes/__init__.py` — the public re-export surface; import from here, not submodules, in new code.

Serialization (`serialization/`):
- `loading.py`: `load_blocks`/`load_boards` (parse `blocks.json`/`boards.json`), `load_game(dir)` (auto-discovers `books/*.json` + `puzzles/*.json` under a `games/<Name>/` dir, builds a full `Game`). Game/book/puzzle names are never read from a JSON `"name"` field -- `Game.name` = the `games/<Name>/` folder name, `PuzzleBook.name`/standalone `Puzzle.name` = the containing JSON file's stem, so identity can't drift from the filename it's loaded from. The one exception is a puzzle *inside* a book file (many puzzles share one file, so there's no per-puzzle filename) -- those keep an explicit required `"name"` field in the JSON. Also: `load_setup_for_puzzle` (cold-start Setup rebuild for `Solution.to_states` fallback), `load_puzzle_info_for_puzzle` (cold-start difficulty/nr_empty_spaces for `Solution.puzzle_info` fallback -- reads the puzzle's JSON directly, no Setup/placements needed), `grid_to_letter_rows`.
- `saving.py`: `save_solutions`/`save_solve_stats` (SolutionBook/SolveStatsBook -> json, either exact path or `<root>/<name>/<idx>/solutions.json`|`stats.json`; auto-picks `flat=(len==1)`), `save_solution_run(solution_book, stats_book, folder, flat=True)` (writes both into one folder -- what `Solution.from_puzzle`/`SolutionBook.from_puzzlebook` call when `save=True`). `game_name`/`book_name`/`puzzle_name` are never written into the JSON at all -- they're fully determined by the folder a run is saved under (mirroring `Source.relative_dir()`) and recovered from it on load (`_game_book_from_run_dir`, `_puzzle_name_from_run_dir`), so there's nothing to drift or need re-parsing. `solutions.json`'s top level is a bare list, not an object -- no sibling metadata means no wrapper key is needed: `flat=True` (a single puzzle's result -- standalone or one puzzle solved out of a book, always via `Solution.from_puzzle`) writes just the list of grids, relying on the folder following `.../<puzzle_name>/<idx>/solutions.json`; `flat=False` (a whole book solved via `SolutionBook.from_puzzlebook`, or `plotting.benchmark`'s per-trial folders that don't follow that convention) writes a list of `{"puzzle_name", "grids"}` objects, always -- even for a one-puzzle book -- since a batch save's folder has no per-puzzle segment to recover a name from (`_read_solutions` tells the two shapes apart by checking whether the first element is a dict). `stats.json` keeps its object wrapper either way since it always carries sibling `mode`/`seed` fields alongside the per-puzzle data. Inverse: `load_solutionbook`/`load_solution`, `load_solve_stats_book`/`load_solve_stats` (the `_solution`/`_stats` singular variants require exactly one puzzle in the file), `load_solution_run(folder)` (loads both back as a pair).
- On-disk layout: `games/<Game>/{blocks.json, boards.json, books/*.json, puzzles/*.json}`; solutions mirror it under `solutions/<Game>/<books|puzzles>/<name>/[<puzzle_name>/]result_<idx>/{solutions.json, stats.json}` -- the optional `<puzzle_name>` segment only appears for one puzzle solved out of a book (see `Source.relative_dir()`); `result_<idx>` is an index-suffixed per-run folder (`result_1`, `result_2`, ...; see `classes._utils._next_free_idx_dir`), not a timestamp, since re-solving the same puzzle/book is expected to reproduce the same solutions but each run still gets its own folder; benchmark runs go under `benchmarks/<Game>/<books|puzzles>/<name>/[<puzzle_name>/]benchmark_<idx>/mode{N}/test{seed}/{solutions.json, stats.json}` (`benchmark_<idx>` via the same `_next_free_idx_dir`, `prefix="benchmark"`, not a timestamp), mirroring the same path `solutions/` uses.

Solving: `Solver.py` / `SolverV2.py` (older/newer backtracking search over a `State`'s placements; modes 0/1/2 = no-pruning/pruning/branching, 3 = + whole-board symmetry, 4 = + open-region symmetry), `compact.py`, `partitioning.py` — solver internals, out of scope for structural review per user. Modes 3 and 4 both work by recursing into one representative per orbit of the branching block's candidate placements and deriving the rest with `_apply_symmetry`; they differ only in where the symmetries come from (`Setup.board_symmetries` filtered by `_active_symmetries` vs. `Setup.region_symmetries` of the node's own open region, memoized in `_region_symmetry_cache`). Mode 4's group always contains mode 3's, and additionally catches symmetric leftover pockets that no rigid motion of the whole board produces. Neither mode looks for symmetry when the branching block has only one candidate placement (a forced move's orbit is itself, so the sweep would be pure cost). `solve(seed=...)` shuffles placement order into a *private shallow copy* of the Setup (`_shuffle_placements`) rather than in place, since the real Setup is shared by every puzzle in the book.

Plotting/benchmarking (`plotting/`): `plot_difficultyspace.py` takes an optional `puzzles` (PuzzleBook/dict) arg and reads difficulty/nr_empty_spaces via `Solution.puzzle_info(puzzles)`. `plot_solve_timeline.py` additionally takes a `stats: SolveStatsBook` (produced alongside the `solutions: SolutionBook` by the same solve call) for duration/elapsed timing data. `benchmark.py` (`run_benchmark`/`load_benchmark`/`plot_benchmark`, runs solves in a subprocess with a wall-clock cap `T`) takes a `Puzzle` (not a bare `State`) and builds a `SolveStats`/`SolveStatsBook` per trial (via `save_solution_run`/`load_solution_run`) since benchmarking is entirely about solve-process metadata, not solutions themselves. `plot_benchmark(stats_books, show_trendline=True, T=None)` draws each trial's cumulative-solutions step curve (anchored at (0,0); N(t) counts solutions found *up to and including* t) plus the per-mode average on a 500-point grid; `T` pins the x-axis to the benchmark's budgeted window rather than to the longest trial observed. Its trendline rate comes from `_poisson_rate`, the textbook homogeneous-Poisson MLE (total solutions / total observed time, pooled over trials) rather than any curve fit -- so the quiet stretches between solutions enter via the denominator instead of being sampled, every second of observation weighs the same, and the line passes exactly through each trial's endpoint. A trial that exhausted its search space early contributes only its own shorter duration.

`main.py` is a scratch/scrapyard of commented-out usage examples, not a real entrypoint — check what's actually uncommented before assuming it reflects current usage patterns.

`constants.py`: grid sentinel values (EMPTY/OUTSIDE_BOARD/UNPLACED) + color tables for difficulty/mode used only in plotting.

Testing: `test_symmetry.py` (run as `python test_symmetry.py`) covers `Setup.region_symmetries` geometry + group axioms, and asserts modes 0/2/3/4 return *identical* solution sets on synthetic symmetric boards, 30 randomly-generated tilings, the `main_puzzles` 40–60 / `pyramid_puzzles` 80–90 ranges and `pyramid_puzzles/100` (hardest pyramid puzzle, mode 4's worst case for per-node overhead) — plus that a seeded solve leaves the shared Setup untouched. Ends with an informational payoff table (placements tried vs. solutions derived by symmetry per mode; modes are timed interleaved and best-of, since whichever runs first otherwise absorbs the cold-start cost). No test runner is configured; tests are plain scripts.
