# Codebase map

Import layering (no cycles): `constants` <- `classes` <- `serialization` <- `solving` <- `benchmark` <- `plotting`. `classes` never imports `serialization`; anything needing both lives in `solving.py`/`serialization/`.

Core model (`classes/`, layered bottom-up):
- `lattice.py` — `Lattice`: geometry of a board/block's axes (orthogonal vs. offset, e.g. triangular/pyramid). Derives gram2 / unit_vectors / `point_group` (every integer matrix `M` with `M.T @ gram2 @ M == gram2`; 8 on the square lattice, 48 on the pyramid's — pure lattice geometry, says nothing about a given board). Leaf, no deps.
- `blocks.py` — `Block` (shape + color/letter + its own Lattice), `BlockCollection` (UserDict, int idx -> Block, unique letters).
- `boards.py` — `Board` (cells: bool ndarray + Lattice), `RegularBoard`, `PyramidBoard(width, depth)` subclasses.
- `setup.py` — `Setup`: board + blocks + **all valid placements** (expensive, computed once, shared by reference across every Puzzle/Book built on it). `placement_cells[block_idx]` = compact cell-index array per valid orientation/position. Compact indexing: grids only cover the board's real cells; `to_full_grid(grid)` / `to_compact_grid(full)` convert to/from the full board-shaped array (used at the rendering / disk boundaries). `render(grid, header=None, leftover_idcs=None)` is a thin facade delegating to `rendering.py`. **Symmetry** (all `cached_property`, built lazily so a solve that can't use symmetry never pays): `cell_coords`, `_point_group_coords`, `_symmetry_tables` (flattens the point-group sweep into integer table lookups on a padded grid) back `region_symmetries(mask)` -> every symmetry of an arbitrary sub-region as a compact-cell permutation that is **the identity outside the mask**, always including the identity; `board_symmetries` is the all-True case (4 on main, 8 on pyramid). `placement_lookup` = `{block_idx: {sorted cells bytes -> placement_idx}}`, which is how a symmetry gets applied to a placement.
- `state.py` — `State`: mutable solve state (grid + chosen_placement_idx, `name` = None) over a shared `Setup`. `place`/`remove` (checked) vs `place_unchecked`/`remove_unchecked` (used by Solver). `.solve(seed, time_limit, max_solutions, up_to_symmetry, **options)` is a plain generator delegating to `Solver` (`up_to_symmetry` is named rather than left in `options` because it changes the solution set, same rule as the two limits); a named state's solutions are renamed "<name> (solution i)"; it prints nothing (progress printing is `solving.py`'s job). `render(show_leftover=True)` (via `_print_header`, overridable) builds header + grid + shape diagrams of any still-unplaced blocks; `__repr__` calls it. `Puzzle(State)`: named, has difficulty, optionally pre-filled from a letter grid (`_initialize_grid`, transposes JSON (depth,width) -> internal (width,depth)); header `"Puzzle {name}"`.
- `puzzlebook.py` — `PuzzleBook(UserDict)`: named collection of Puzzles sharing one Setup. `__repr__` expands every Puzzle with `show_leftover=False`.
- `game.py` — `Game`: top-level container of `books` (name->PuzzleBook), `puzzles` (standalone), `setups` (board_key->Setup). One Game per `games/<GameName>/` folder.
- `source.py` — `Source` (frozen dataclass): game/book/puzzle name triple recording where a Puzzle/Book was loaded from. `relative_dir()` -> `<game>/books/<book>` (book), `<game>/puzzles/<puzzle>` (standalone), `<game>/books/<book>/<puzzle>` (one puzzle out of a book). Set by `serialization.loading.load_game`, `None` for hand-built objects.
- `solutions.py` — pure data containers, no solving or I/O: `PuzzleInfo` (difficulty, nr_empty_spaces — the source Puzzle's, never stored on `Solution`), `SolveStats` (puzzle_name, options, seed, duration, elapsed; `options` = free-form solver kwargs besides the seed (`symmetry`, `order`), kept to tell solver variants apart in benchmarks; only options that leave the solution set alone belong there), `Solution` (puzzle_name + full board-shaped `grids` + game/book_name (transient, recovered from the save folder on load) + optional live `puzzle`; `to_states(setup)` and `puzzle_info(puzzles)` only use the live puzzle/setup given — for a Solution loaded from disk use `serialization.solution_states` / `solution_puzzle_info`; `__repr__` renders when a live puzzle exists, else a one-line summary), `SolutionBook` and `SolveStatsBook` (UserDicts keyed by puzzle_name with book-level game/book_name (+ options/seed for stats); `.name` computed via `_book_name`).
- `solver.py` — `Solver`, out of scope for structural review. Exhaustive exact cover: `Solver(state).solve(seed=None, time_limit=inf, max_solutions=inf, symmetry=True, up_to_symmetry=False, order=None)` yields every solution as a `state.copy()`, stopping early once either limit is hit (time checked once per node; a sticky `stopped` flag unwinds the recursion so the Solver stays reusable — nothing ever `break`s out of a `for ... in search(...)` loop, which would abandon a generator mid-placement). **Items**: cells and blocks share one index space (`0..n_cells-1` cells, `n_cells + block position` blocks, `n_cols` = the padding column, parked at `_COVERED`) — "cell covered once" and "block placed once" are the same constraint — so a single `counts` array, one decrement and one argmin serve both the dead-end check and the branch choice. **Branching**: `_branch_item` takes the scarcest item overall, cell or block, in one argmin over both (count 0 = dead end, `_COVERED` = solved, i.e. everything satisfied). There is no mode to pick — the cell-only / block-only / hybrid rules were measured head to head and removed on 2026-09-23 (`SYMMETRY_NOTES.md` §6; `c398a8b` is the last commit with all four). `_block_branch` (the scarcest *block*) survives as `orbit_branch`'s only branch set, being the only one a symmetry carries onto itself. `order` (None = on exactly when a limit is set) sorts candidates via `_order_gids` (lexicographic by their cells' sorted live-placement counts, `_priority` breaking ties): it finds the first solutions sooner, but a full enumeration visits the same nodes whatever order siblings are tried in, so there it is ~25% pure overhead. **Symmetry**: `Setup.region_symmetries` is called **once per solve**, on the root's open cells; every group used deeper is that one filtered (`_orbits` returns each representative's stabilizer for free), so there is no per-node geometry sweep. `orbit_branch` searches one placement per orbit and derives the rest via `_transform`; `up_to_symmetry` yields only the representatives, which is exactly one per symmetry class and strictly less work. Solution *set* is identical across every mode; order is not (a solution is followed by its images), and derived solutions count towards `max_solutions` — both counters increment *before* their yield, since a suspended generator hasn't resumed when an enclosing `orbit_branch` reads `stopped`. **Flat state**: `_Tables` lays every block's placements end to end — `placement_rows` (each placement's cells, padded with `n_cols`), `placement_items` (those cells plus the block's own column), `block_start` (block position `p` owns global ids `block_start[p]:block_start[p+1]`), `block_of`, `item_lists[i]` (every placement satisfying item i), lazily cached `kill(gid)` (everything overlapping it, plus the rest of its block). It depends on the `Setup` alone, so it is built once per Setup and shared by every Solver on it through the module-level weak cache `_tables_for` — worth 1.47x/2.09x over a whole book, nearly all of it `kill`'s memo staying warm rather than the build. It is deliberately *not* an attribute on `Setup`: `benchmark.py` pickles a Puzzle per trial, and a warm cache in `Setup.__dict__` would take that pickle from 0.18 MB to 8 MB. A node is `(live, counts, item)`; `_root_node` builds the first, `_place` derives each child **and rejects it right there if it is already dead** (forward checking — no dead child ever costs a recursion; `live` is copied only once the child survives). The search never touches a grid: it carries a `path` of global ids and replays it onto `state.copy()` at a solution (`snapshot`). **Seeds**: never reorder `Setup.placements`; a seed draws random tie-break priorities per placement/item once per solve (`None` unseeded, so argmin's own index order breaks ties). `SYMMETRY_NOTES.md` has the measurements, and the two things deliberately left out (symmetric leftover *pockets*, and partitioning the open region into connected components).
- `rendering.py` — terminal display: `grid_lines`, `block_shape_lines`, `legend_lines`, `render(board, blocks, grid, header=None, leftover_idcs=None)`. Plain `Board`/`BlockCollection`/grid args, no `Setup` dependency.
- `_utils.py` — `_assert_unique`, `_shared` (dedup/consistency helpers).
- `__init__.py` — the public re-export surface; import from here, not submodules, in new code.

Serialization (`serialization/`; imports `classes`):
- `loading.py`: `load_blocks`/`load_boards`, `load_game(dir)` (auto-discovers `books/*.json` + `puzzles/*.json`, builds a full `Game`). Names are never read from a JSON `"name"` field except for puzzles inside a book file: `Game.name` = folder name, `PuzzleBook.name`/standalone `Puzzle.name` = file stem. A board's optional `"cells"` is row strings (`"X"` = cell). Book-file parsing is shared via `_read_book_file`/`_read_puzzle_file`. Cold-start helpers for Solutions loaded from disk: `load_setup_for_puzzle`, `load_puzzle_info_for_puzzle` (reads JSON only, no Setup), and their Solution-level entry points `solution_states(solution)` / `solution_puzzle_info(solution, puzzles=None)` (live puzzle / `puzzles` first, else the game files).
- `jsonio.py`: leaf letter-grid helpers. A grid is one string per row (`"BBB        "`), a pyramid a list of such layers; `" "` = empty/off-board. `parse_letter_grid`, `letter_grid_to_rows` (from internal (width, depth[, height])), `dump_json(obj, path)` (indent 2, list of strings one row per line).
- `paths.py`: leaf; where runs live and how to read names back from a path: `next_free_idx_dir(base, prefix="result")` (`result_1`, `result_2`, ...; `benchmark` prefix for benchmarks), `next_run_dir(source, root)`, `game_book_from_run_dir`, `puzzle_name_from_run_dir`, `single_entry`.
- `solutions_io.py`: `write_solutions`, `load_solutionbook`. solutions.json stores grids as letter rows (block letter from the live puzzle's blocks, else the game's `blocks.json`; non-block -> `" "`). Top level is a bare list: `flat=True` (one puzzle; name recovered from `.../<puzzle_name>/<idx>/`) writes just the grids, `flat=False` (whole book, or benchmark trial folders) writes `{"puzzle_name", "grids"}` objects; `load_solutionbook` tells them apart by the first element.
- `stats_io.py`: `write_solve_stats`, `load_solve_stats_book`. stats.json keeps an object wrapper (`options`, `seed`, then per-puzzle data); `_read_options` folds the legacy top-level solver flags into `options` so old runs still load.
- `runs.py`: `save_solution_run(solution_book, stats_book, folder, flat=True)` / `load_solution_run(folder)` — the solutions + stats pair in one folder.
- game/book/puzzle names are never written into JSON; they follow from the folder. On-disk layout: `games/<Game>/{blocks.json, boards.json, books/*.json, puzzles/*.json}`; solutions mirror it under `solutions/<Game>/<books|puzzles>/<name>/[<puzzle_name>/]result_<idx>/{solutions.json, stats.json}`; benchmarks under `benchmarks/<Game>/<books|puzzles>/<name>/[<puzzle_name>/]benchmark_<idx>/<config-label>/test{seed}/{solutions.json, stats.json}`. `solutions/` and `benchmarks/` are git-ignored.

Running (`solving.py`, `benchmark.py` at the repo root):
- `solving.py`: `solve_puzzle(puzzle, seed, verbose, save, path, solutions_root, time_limit, max_solutions, up_to_symmetry, **options) -> (Solution, SolveStats)` and `solve_puzzlebook(book, ...) -> (SolutionBook, SolveStatsBook)` (one combined `flat=False` save). Solves, times, packages (`make_result`, `single_run_books`) and auto-saves under `solutions/` mirroring the `Source`. `time_limit`/`max_solutions`/`up_to_symmetry` are deliberately not part of `options` (never recorded or treated as a benchmark config): they change which solutions come back, not how they are found. `verbose` is a `Verbosity` IntEnum (cumulative): `SILENT` 0; `SUMMARY` 1 "Found 21 solutions to puzzle x in 1.23s"; `EACH_SOLUTION` 2 also "Found 3rd solution to puzzle x in 0.42s" per solution; `SHOW_SOLUTIONS` 3 prints each solved puzzle instead of that line (its header already names puzzle + solution number). The summary line ends every level >= 1 (at level 3 it omits "to puzzle x" when a puzzle was rendered above it).
- `benchmark.py`: `run_benchmark`/`load_benchmark`, `config_key`/`config_label` (a config = dict of solver keyword options; `DEFAULT_CONFIGS = [{}, {"symmetry": False}, {"order": False}]`). Trials run in a subprocess with a wall-clock cap `T`: the parent owns the authoritative deadline and kills the worker, which also gets `time_limit=T`. Takes a `Puzzle`; builds one-entry books per trial via `solving.make_result`/`single_run_books`.

Plotting (`plotting/`): `plot_difficultyspace.py` and `plot_solve_timeline.py` (also takes a `SolveStatsBook` for timing) read difficulty/nr_empty_spaces via `serialization.solution_puzzle_info(sol, puzzles)`. `plot_benchmark.py`: `plot_benchmark(stats_books, show_trendline=True, T=None)` draws each trial's cumulative-solutions step curve (anchored at (0,0)) plus the per-config average on a 500-point grid, colored from `constants.CONFIG_PALETTE`; `T` pins the x-axis to the budgeted window. Trendline rate = `_poisson_rate`, the homogeneous-Poisson MLE (total solutions / total observed time, pooled over trials).

`main.py` is a scratch file of mostly commented-out usage examples, not a real entrypoint. `main.ipynb` is a demo notebook.

`constants.py`: grid sentinels (EMPTY/OUTSIDE_BOARD/UNPLACED), `SOLUTION_DIR`/`BENCHMARK_DIR`/`GAMES_DIR` (Paths), color tables used only in plotting.

Testing (`tests/`, stdlib `unittest`; run the whole suite by running `run_tests.py` in the repo root, ~7 s; nothing is read from or written to `solutions/`/`benchmarks/`): `tests/data/<Game>/<book>.json` -- hand-checked solutions used as a fixture (`{puzzle name: [solution, ...]}`, a solution being a list of layers (1 on main/alt boards, 5 on a pyramid) of row strings, `" "` = off-board). IQpuzzler holds one sampled puzzle per difficulty per book; IQpuzzlerPRO holds every puzzle, verified against the solution booklet. Loaded by `_helpers.load_known_solutions`. `test_solver.py` -- known solutions must be valid and among the solver's; every PRO puzzle's booklet solution must be found and every PRO puzzle must have exactly one solution (`pyramid_puzzles/120` intentionally FAILS: the real game's claim doesn't hold there, 5 solutions); an unsolvable hand-built puzzle has no solution; seeds give identical solution sets; the first 25 solutions of the empty boards are valid and distinct; time/count limits. `test_symmetry.py` -- the geometry (`point_group`/`region_symmetries` group axioms, images being the identity outside their region) and the orbit reduction on top of it: `symmetry` on and off, plus `order` forced on and off, give an identical solution set on the symmetric book puzzles, an asymmetric one, and the unsolvable fixture (`symmetry=False` is the baseline the rest are checked against — it derives no solution from another); derived solutions are valid; `up_to_symmetry` counts (main_puzzles 11/12/17-20/35/65 -> 1, 22 -> 2), its representatives regenerate the full set under the group and are pairwise non-symmetric; PRO pyramid 81/82/90 (symmetric region, one self-symmetric solution) stay at one solution in every mode; `max_solutions` stays exact once derived solutions count. The 12 pentominoes on 3x20 check total (8) and up-to-symmetry (2) counts against published numbers; 4x15/5x12/6x10 are the same check by hand, too slow for the suite. `test_data.py` -- puzzle-file sanity (blocks-fill-board is enforced by `Setup._validate` at load time, not tested separately). No tests for terminal output formatting. `test_serialization.py` -- letter-grid helpers and a save/load round trip of solutions.json (temp folder only). `_helpers.assert_valid_solution` is the shared validity check.
