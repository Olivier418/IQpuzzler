# Codebase map

Import layering (no cycles): `constants` <- `classes.kernel` <- `classes` <- `serialization` <- `solving` <- `benchmark` <- `plotting`. `classes` never imports `serialization`; anything needing both lives in `solving.py`/`serialization/`. `classes/kernel.py` is a leaf below the rest of `classes`: it imports only numpy and numba and knows nothing about Setup/State/Puzzle.

Core model (`classes/`, layered bottom-up):
- `lattice.py` — `Lattice`: geometry of a board/block's axes (orthogonal vs. offset, e.g. triangular/pyramid). Derives gram2 / `unit_vectors` (every direction of unit length, used by `Setup._valid_orientations` and by the kernel's cell-adjacency table). Leaf, no deps.
- `blocks.py` — `Block` (shape + color/letter + its own Lattice), `BlockCollection` (UserDict, int idx -> Block, unique letters).
- `boards.py` — `Board` (cells: bool ndarray + Lattice), `RegularBoard`, `PyramidBoard(width, depth)` subclasses.
- `setup.py` — `Setup`: board + blocks + **all valid placements** (expensive, computed once, shared by reference across every Puzzle/Book built on it). `placement_cells[block_idx]` = compact cell-index array per valid orientation/position. Compact indexing: grids only cover the board's real cells; `to_full_grid(grid)` / `to_compact_grid(full)` convert to/from the full board-shaped array (used at the rendering / disk boundaries). `render(grid, header=None, leftover_idcs=None)` is a thin facade delegating to `rendering.py`. Two lazy `cached_property` tables: `cell_coords` (compact index -> board position) and `kernel_tables` = `(kernel.Tables, block_ids)`, built once per Setup and shared by every Solver on it — a book is 72 puzzles on one Setup, so caching it here rather than per puzzle is worth ~2x on a book solve. The search's *mutable* state (`kernel.Workspace`) deliberately does NOT live here. `warmup()` builds `kernel_tables` and loads the compiled kernel (`kernel.warmup`, once per process); `solving.solve_puzzle` and `benchmark` call it before their clocks start so numba's ~0.35 s cache load (seconds on a recompile) isn't billed to the first puzzle.
- `state.py` — `State`: mutable solve state (grid + chosen_placement_idx, `name` = None) over a shared `Setup`. `place`/`remove` (checked) vs `place_unchecked`/`remove_unchecked` (used by Solver). `nr_empty_spaces` property. `.solve(seed, time_limit, max_solutions, **options)` is a plain generator delegating to `Solver`; a named state's solutions are renamed "<name> (solution i)"; it prints nothing (progress printing is `solving.py`'s job). `render(show_leftover=True)` (via `_print_header`, overridable) builds header + grid + shape diagrams of any still-unplaced blocks; `__repr__` calls it. `Puzzle(State)`: named, has difficulty, optionally pre-filled from a letter grid (`_initialize_grid`, transposes JSON (depth,width) -> internal (width,depth)); header `"Puzzle {name}"`.
- `puzzlebook.py` — `PuzzleBook(UserDict)` (raises `ValueError` if empty): named collection of Puzzles sharing one Setup. `__repr__` expands every Puzzle with `show_leftover=False`.
- `game.py` — `Game`: top-level container of `books` (name->PuzzleBook), `puzzles` (standalone), `setups` (board_key->Setup). One Game per `games/<GameName>/` folder.
- `source.py` — `Source` (frozen dataclass): game/book/puzzle name triple recording where a Puzzle/Book was loaded from. `relative_dir()` -> `<game>/books/<book>` (book), `<game>/puzzles/<puzzle>` (standalone), `<game>/books/<book>/<puzzle>` (one puzzle out of a book). Set by `serialization.loading.load_game`, `None` for hand-built objects.
- `solutions.py` — pure data containers, no solving or I/O: `SolveStats` (puzzle_name, options, seed, duration, elapsed; `options` = free-form solver kwargs besides the seed (`branch`, `order`), kept to tell solver variants apart in benchmarks; only options that leave the solution set alone belong there), `Solution(puzzle, grids)` (full board-shaped `grids`; **always holds its live `puzzle`** — the one solved, or the one `load_solution_run` found in `games/` (or the `game` given) — so `puzzle_name`/`setup` are properties and difficulty/empty spaces are read off `sol.puzzle`; `to_states()`), `SolutionBook` and `SolveStatsBook` (UserDicts keyed by puzzle_name with a book-level `book_name` (+ options/seed for stats); `.name` computed via `_book_name`).
- `solver.py` — `Solver`, the thin Python driver around `kernel.py`. Exhaustive exact cover: `Solver(state).solve(seed=None, time_limit=inf, max_solutions=inf, order=None, branch="both")` yields every solution as a `state.copy()`, stopping early once either limit is hit. It owns only what the kernel cannot see: `_start()` turns the State's grid + already-placed blocks into the kernel's `(occ, used)`; `_resolve_rules()` (module level) resolves `branch`/`order` to integer codes; `_emit()` replays a path of global ids through `place_unchecked`, so grid and `chosen_placement_idx` can never disagree. **Laziness**: the kernel is never told `max_solutions`; it gets a solution-buffer cap and a node budget, returns FULL/BUDGET/DONE, and is re-entered with its stack intact. An EMA of nodes/s sizes ~2 ms chunks (`_next_budget`), which is how `time_limit` stays exact to ~2 ms and how the generator stays abandonable mid-tree. The workspace is allocated per kernel entry and never stored, so a reused Solver gives bit-identical output with no reset discipline. **`branch`** picks which kind of item a node branches on (see `kernel.choose_item`): `"both"` (default, the scarcer of the two), `"cell"`, `"block"` — `"block"` is a baseline only, hopeless on an open board. **`order`** ranks a node's candidates; because `kernel.rank` keys off a *placement* and never learns which kind of item was branched on, it applies uniformly to all three `branch` modes. `True`/`"counts"`, `"pockets"`, `"fanout"`; `None` = on iff a limit is set. Seeded with `order=False` sorts by the drawn priority alone, since the branch argmin leaves nothing for a seed to perturb. `SOLVER_WALKTHROUGH.md` is a read-alongside guide to both files; `SOLVER_NOTES.md` has the measurements and what was removed (symmetry, partitioning) and why.
- `kernel.py` — the search itself, compiled by numba; no `classes` imports. A cell is a bit: occupancy is `occ`, `NW = ceil(n_cells/64)` uint64 words, and `pmask[gid]` is the same for a placement, so the conflict test is one AND per word. `nw` is read from `occ.shape[0]` at runtime and looped over, so there is **no cell-count ceiling and no separate path for big boards** — 55 cells and IQquub's 64 both give NW 1; a 200-cell board gives NW 4 and works. `Tables` (per Setup, via `Setup.kernel_tables`, ~70 KB): `pmask`, `pblock`, `pcells`, `psize`, CSR `cell_start`/`cell_pl`, `block_start`, `full`, `neigh`, `fan` = `max(cell degree, block run)` so both kinds of candidate list fit one buffer. `Workspace` = one run's mutable state, allocated per entry. `kernel()` is an **iterative explicit-stack DFS** — numba recursion segfaults, and a stack is what makes the run resumable; every `return` happens with the loop invariant intact, so re-entry is just "run the loop again". `occ == full` is the only termination test: `Setup._validate_area` guarantees the blocks' total area equals the board's, so covering every cell implies placing every block — and the converse, which is what makes `branch="block"` terminate. A placement is its own undo (`^=`). `choose_item` returns `(kind, index)` — kind 0 a cell, 1 a block position — and is what a node costs, not the conflict test; `_count_cell`/`_count_block` cap their scans at the best-so-far count, which is what makes MRV affordable. **Debugging: `NUMBA_DISABLE_JIT=1` runs this exact source as plain Python** (~1300x slower, pdb works) — that is why there is one implementation and no NumPy reference. It constrains the source: index the `BIT` table instead of shifting (numpy 2 promotes `uint64 << int` to float64) and write every literal `np.uint64(...)`. All helpers are module-level — a closure cell would be hashed into numba's `cache=True` key and `benchmark.py`'s trial subprocesses would recompile. `warmup(t)` (idempotent, module flag) compiles/loads once: `benchmark.py` calls it in the parent so trial subprocesses don't race, and in each worker before its "ready" handshake.
- `rendering.py` — terminal display: `grid_lines`, `block_shape_lines`, `legend_lines`, `render(board, blocks, grid, header=None, leftover_idcs=None)`. Plain `Board`/`BlockCollection`/grid args, no `Setup` dependency.
- `_utils.py` — `_assert_unique`, `_shared` (dedup/consistency helpers).
- `__init__.py` — the public re-export surface; import from here, not submodules, in new code.

Serialization (`serialization/`; imports `classes`):
- `loading.py`: `load_blocks`/`load_boards`, `load_setups(game_dir)` ({board_key: Setup}), `load_book(game_dir, book_name, setups)`, `load_standalone_puzzles(game_dir, setups)`, `load_game(dir)` (auto-discovers `books/*.json` + `puzzles/*.json` via those two, builds a full `Game`); every loaded book/puzzle gets its `Source`. `save_puzzlebook(book, game, games_root=GAMES_DIR)` is the inverse for a book made in memory (e.g. `most_difficult_puzzles`): writes `games/<game>/books/<name>.json` (never overwrites), sets the Sources, adds it to `game.books` — a run can only be saved for puzzles that live in `games/`. Names are never read from a JSON `"name"` field except for puzzles inside a book file: `Game.name` = folder name, `PuzzleBook.name`/standalone `Puzzle.name` = file stem. A board's optional `"cells"` is row strings (`"X"` = cell).
- `puzzles_io.py`: the book-file format (`{"board", "puzzles": [{"name", "difficulty", "grid"}]}`, or a bare list for board "main"), read and written: `read_book_file`, `puzzle_from_entry`, `load_puzzles(file, setups)`, `write_puzzles(puzzles, board_key, file)`.
- `jsonio.py`: leaf letter-grid helpers. A grid is one string per row (`"BBB        "`), a pyramid a list of such layers; `" "` = empty/off-board. `parse_letter_grid`, `letter_grid_to_rows` (from internal (width, depth[, height])), `block_grid_to_rows`/`rows_to_block_grid` (full grid of block indices <-> letter rows via the blocks' letters), `dump_json(obj, path)` (indent 2, list of strings one row per line).
- `paths.py`: leaf; where runs live and how to read names back from a path: `next_free_idx_dir(base, prefix="result")`, `next_run_dir(source, root, prefix="result")` (raises for a source-less puzzle/book, pointing at `save_puzzlebook`; `benchmark` prefix for benchmarks), `game_book_from_run_dir`, `puzzle_name_from_run_dir` (the folder below `books/<book>/` or `puzzles/`; both anchor on the nearest `books`/`puzzles` component, so benchmark config/seed folders below are fine, and raise for a path outside the layout).
- `solutions_io.py` / `stats_io.py`: `write_solutions`/`load_solutionbook(file, puzzles, flat_name, book_name)`, `write_solve_stats`/`load_solve_stats_book(file, flat_name, book_name)`, `single_entry`. Grids are letter rows. `flat=True` (one puzzle; name from the path) writes just the grids / duration+elapsed, `flat=False` (whole book, benchmark trials) per-puzzle `{"puzzle_name", ...}` entries. stats.json keeps an object wrapper (`options`, `seed`); old-format runs (top-level solver flags) are not supported.
- `runs.py`: `save_solution_run(solution_book, stats_book, folder, flat=True)` / `load_solution_run(folder, game=None)`. A run folder is `solutions.json` + `stats.json` only — no puzzles, since `games/` is fixed (existing puzzles never change; `save_puzzlebook` only adds books), so a reference to it can't go stale: its path (any root, ending in the `Source.relative_dir()` layout) names game/book/puzzle, and the Puzzles come from `game` when given (the same objects as in memory), else from `games/` (`load_book`/`load_standalone_puzzles` on `_game_setups`, lru-cached per game per process).
- game/book/puzzle names are never written into JSON (except `puzzle_name` in a `flat=False` file); they follow from the folder. On-disk layout: `games/<Game>/{blocks.json, boards.json, books/*.json, puzzles/*.json}`; solutions mirror it under `solutions/<Game>/<books|puzzles>/<name>/[<puzzle_name>/]result_<idx>/{solutions.json, stats.json}`; benchmarks under `benchmarks/<Game>/<books|puzzles>/<name>/[<puzzle_name>/]benchmark_<idx>/<config-label>/test{seed}/{solutions.json, stats.json}`. `solutions/` and `benchmarks/` are git-ignored.

Running (`solving.py`, `benchmark.py` at the repo root):
- `solving.py`: `solve_puzzle(puzzle, seed, verbose, save, path, solutions_root, time_limit, max_solutions, **options) -> (Solution, SolveStats)` and `solve_puzzlebook(book, ...) -> (SolutionBook, SolveStatsBook)` (one combined `flat=False` save). Solves, times, packages (`make_result`, `single_run_books`) and, only with `save=True` (opt-in), saves under `solutions/` mirroring the `Source` (or to `path=`). `time_limit`/`max_solutions` are deliberately not part of `options` (never recorded or treated as a benchmark config): they change which solutions come back, not how they are found. `verbose` is a `Verbosity` IntEnum (cumulative): `SILENT` 0; `SUMMARY` 1 "Found 21 solutions to puzzle x in 1.23s"; `EACH_SOLUTION` 2 also "Found 3rd solution to puzzle x in 0.42s" per solution; `SHOW_SOLUTIONS` 3 prints each solved puzzle instead of that line (its header already names puzzle + solution number). The summary line ends every level >= 1 (at level 3 it omits "to puzzle x" when a puzzle was rendered above it).
- `benchmark.py`: `run_benchmark`/`load_benchmark(folder, game=None)`, `config_key`/`config_label` (a config = dict of solver keyword options; `DEFAULT_CONFIGS` = a tuple of four `order` configs (`counts`, `pockets`, `fanout`, `False`)). Trials run in a subprocess with a wall-clock cap `T`: the parent owns the authoritative deadline and kills the worker, which also gets `time_limit=T`. Takes a `Puzzle` that lives in `games/` (has a `source`); builds one-entry books per trial via `solving.make_result`/`single_run_books`.

Plotting (`plotting/`): `plot_puzzlebook.py`: `plot_puzzlebook(solutions, stats=None, x=None, y=None, z=None, frontier_difficulty=FRONTIER_DIFFICULTY, title=None, ax=None)` is the one general one-dot-per-puzzle scatter, colored by difficulty; `z` makes it 3D (log axes become log10 with 10^k tick labels, since 3D can't log-scale). Axes are named `Metric`s from `METRICS` (`nr_empty_spaces`, `nr_solutions`, `time_to_first_solution`, `time_to_last_solution`, `solve_time`; the timing ones need `stats`), or a custom `Metric(label, value(sol, stats), log, needs_stats)`. Puzzles with an undefined value (nan) or a non-positive one on a log axis are dropped. Difficulty/nr_empty_spaces are read off `sol.puzzle`; puzzles on the same point (values + color) are consolidated into one dot labeled with all their names; an existing `ax` is an overlay: it remembers its metrics (`ax._puzzlebook_metrics`), so `x`/`y`/`z` are inherited (naming a different one raises), and its legend is extended, not rebuilt. `plot_solve_timeline(solutions, stats, ax=None)` is deliberately standalone: it draws one mark per *solution* rather than one dot per puzzle. `plot_benchmark.py`: `plot_benchmark(stats_books, show_trendline=True)` draws each trial's cumulative-solutions step curve (anchored at (0,0)) plus the per-config average on a 500-point grid, colored from `constants.CONFIG_PALETTE`; Trendline rate = `_poisson_rate`, the homogeneous-Poisson MLE (total solutions / total observed time, pooled over trials).

`placements.py` (root): `placement_counts(game) -> {board_key: {block_idx: n placements}}` and `print_placement_table(game)` (rows = pieces drawn via `rendering.block_shape_lines`, columns = boards; needs `game.setups`).

`most_difficult_puzzle.py` (root): `most_difficult_puzzles(start, difficulty=FRONTIER_DIFFICULTY, verbose=True)` (raises `ValueError` if nothing beats `start`) searches a Puzzle's Setup for puzzles that beat it and returns the Pareto frontier as `(PuzzleBook, SolutionBook, SolveStatsBook)`, the puzzles named A, B, C, ... (solved via `solving.solve_puzzlebook`, so its imports sit above `solving`). Subsets are visited by decreasing empty spaces, each searched under `_ceiling` (the most solutions it could have and still survive the frontier so far); once that is < 1 the subset is skipped outright. The empty board is excluded on purpose.

`main.py` is a scratch file of mostly commented-out usage examples, not a real entrypoint. `main.ipynb` is a demo notebook.

`constants.py`: grid sentinels (EMPTY/OUTSIDE_BOARD/UNPLACED), `SOLUTION_DIR`/`BENCHMARK_DIR`/`GAMES_DIR` (Paths), color tables used only in plotting.

Testing (`tests/`, stdlib `unittest`; run the whole suite by running `run_tests.py` in the repo root, ~6 s; nothing is read from or written to `solutions/`/`benchmarks/`): `tests/data/<Game>/<book>.json` -- hand-checked solutions used as a fixture (`{puzzle name: [solution, ...]}`, a solution being a list of layers (1 on main/alt boards, 5 on a pyramid) of row strings, `" "` = off-board). IQpuzzler holds one sampled puzzle per difficulty per book; IQpuzzlerPRO holds every puzzle, verified against the solution booklet. Loaded by `_helpers.load_known_solutions`. `test_solver.py` -- known solutions must be valid and among the solver's; every PRO puzzle's booklet solution must be found and every PRO puzzle must have exactly one solution (`pyramid_puzzles/120` is skipped there and pinned as an `expectedFailure`: the real game's claim doesn't hold, 5 solutions); an unsolvable hand-built puzzle has no solution; seeds give identical solution sets; the first 25 solutions of the empty boards are valid and distinct; time/count limits. `test_branching.py` -- `branch` (`cell`/`block`/`both`) and `order` (forced on and off) change the route, never the destination: identical solution sets on a spread of book puzzles and on the unsolvable fixture, with `branch="cell"` as the baseline the rest are checked against; solutions stay valid in every mode; `max_solutions` stays exact in every mode; unknown `branch`/`order` names raise. `branch="block"` is pathologically slow on an open board (no solution to `empty_main` in 30 s), so `OPEN_MODES` leaves it out of the two tests that start from one. The 12 pentominoes on 3x20 check the total (8) against a published number; 4x15/5x12/6x10 are the same check by hand, too slow for the suite. `test_data.py` -- puzzle-file sanity (blocks-fill-board is enforced by `Setup._validate_area` at load time, not tested separately). No tests for terminal output formatting. `test_serialization.py` -- letter-grid helpers and run-folder round trips (temp folder only): one puzzle (from `games/` and from an in-memory `game`), a whole book, and a new book given a home with `save_puzzlebook` before its run can be saved. `_helpers.assert_valid_solution` is the shared validity check.
